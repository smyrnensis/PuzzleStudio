PuzzleStudio reads .puzzle files. Each puzzle block declares its own dimension and owns its objects, levels, rules, lifecycle, and presentation.

Basic Path

Read the Basic pages in order when making your first game.

Puzzle Block defines the playable model. Layers, Legend, and Levels make a board that the editor can load. Rewrite Rules, Input Rules, and Movement make it respond to input. Win Conditions make a level finish, and Visuals make declared objects visible.

Advanced Path

Read Advanced pages when the basic game needs another capability.

Advanced is organized by authoring task: Rules & Patterns, State & Lifecycle, Objects & Selectors, Levels, Scenes & UI, Visuals, 3D, and Sound. Choose the chapter for the task you are doing instead of reading Advanced as one long sequence.

First Editing Loop

Change the level first, then the legend, then the rules. That keeps each edit visible.

Add a character to the level.

Map that character in legend.

Put it in a layer.

Give the object a visual if it should be visible. A 3D object without a visual is not given an implicit cube.

Add rules only after it appears correctly.

PuzzleStudio Documents

Puzzle Block

Use a puzzle block for one playable ruleset.

puzzle sokoban {
layers {
Goal
Player Box Wall
}

win_conditions {
all Goal on Box
}

rules {
input [ Player ] -> [ > Player ]
[ > Player | Box ] -> [ > Player | > Box ]
move
}

levels {
legend {
. = empty
# = Wall
P = Player
B = Box
G = Goal
}

level "start" {
#####
#PBG#
#####
}
}
}

A puzzle usually contains layers, visuals, rules, win conditions, and levels. rules { ... } is the required gameplay entry point; the removed transitions, main, and rule forms are not alternatives.

One puzzle may split rules, on_level_start, on_level_clear, on_last_level_clear, levels, or visuals across several blocks. Fragments of the same kind are joined in source order and share one owner scope, so names declared in a later fragment are visible to earlier fragments.

Files can contain more than one puzzle when scenes need to switch between them. Use puzzle for a 3D model. Both model kinds use levels { ... }; levels3 is no longer syntax.

Reuse Inside A Document

Use asset and import when several owners in the same .puzzle document share authored declarations.

asset shared_presentation {
visuals {
Player {
#4f7cff
0
}
}
sounds {
sfx step { seed = step; type = step }
}
}

puzzle sokoban {
import shared_presentation
}

An asset stores syntax without interpreting it. import delivers that syntax to the receiving owner, which validates it as ordinary body content. Assets are lexically scoped; an inner asset with the same name shadows its ancestor. Unknown assets, duplicate imports, and import cycles are errors.

Each .puzzle file is an independent game document. asset does not load another file, and the language has no cross-file import syntax. Image, audio, and font files are referenced directly by visuals, sounds, and theme.

PuzzleStudio Documents

Layers

Use layers to declare board objects, state exclusion, and back-to-front drawing order. There is no separate objects or visual-order block.

puzzle sokoban {
layers {
Goal Button
Player Box Wall
}
}

Objects on the same state layer cannot occupy the same cell at the same time.

Most layers do not need names. Use a named layer when you also want a selector alias:

layers {
solid = Player Box Wall
}

Then a rule can use solid to mean Player Box Wall. Use groups for selector aliases that should not also define state-layer exclusion. Visual drawing order is the declaration order in layers.

Prefix a visual resource with ! to place a transient animation without adding it to state storage. Box !Box is valid: the first name is the object and the second is the animation visual.

Declare directional priority directly in layers. Use two distinct axes in 2D and three in 3D:

layers {
priority = down right
Floor
Box !Push
}

merge keeps its rows as separate state layers while combining them into one global drawing priority:

layers {
Floor
merge {
actor = Player Box
marker = Goal
effect = !Burst
}
}

Instances from the same owner cell inside a merge use unordered average composition. Directional priority still orders different owner cells. Use ordinary layer rows when visuals need a strict under/over relationship.

Use each to expand selector alternatives into separate ordinary layers, or for to generate layer rows from a tag set:

tags {
kind = red blue
}
layers {
each Player Box Wall
for k in kind {
k = Gem:k Door:k
}
}

Every expanded row is a normal state layer with the usual exclusion and drawing semantics. each does not accept animation visuals.

PuzzleStudio Documents

Legend

Use legend to map level characters to objects.

levels {
legend {
# = Wall
P = Player
B = Box
G = Goal
* = Goal Box
+ = Goal Player
}
}

Each non-empty character used in a level map should have a legend entry. . is reserved as empty in both 2D and 3D, so it needs no entry. . = empty may be written explicitly, but . cannot be remapped and another character cannot be assigned to empty.

The right side must resolve to objects or selectors already declared by layers; a legend entry never creates an object.

One character can place multiple objects in the same cell, such as Goal Box.

PuzzleStudio Documents

Levels

Use levels to store playable maps.

levels {
level first
#####
#PBG#
#####

level second
#######
#P.BG#
#######
}

Each non-empty row after an unbraced level <name> is read as level text until a blank line, another level, or the end of the block. Unbraced levels contain only map rows. Use level <name> { ... } for local declarations or lifecycle behavior.

2D and 3D models both use levels. A 3D level separates Z layers with a line containing only -; the removed levels3 block is not accepted. In both dimensions, . is the reserved empty cell and needs no legend entry.

A braced level can own a local legend and turn-rule additions. before_rules runs before the puzzle rules, while after_rules runs afterward.

level tutorial {
legend {
x = Goal Box
}
before_rules {
once [ Box ] -> [ Box{armed} ]
}
P.x
after_rules {
once [ Box{armed} ] -> [ Box ]
}
}

Several levels { ... } blocks in one puzzle form one level pack in source order. Their legends and declarations share the complete levels scope.

Use next_level from rules or lifecycle hooks to advance.

PuzzleStudio Documents

Rewrite Rules

Rules describe local state changes.

rules {
[ Player | Box ] -> [ Player | Crate ]
}

A rewrite has a left side, an arrow, and a right side.

Cells inside a row pattern are separated by |. A selector such as Player or Box matches an object in that cell.

Use no <selector> when a board cell must not contain an object. Use null when the pattern cell itself must be outside the stage.

rules {
once right [ no Edge | null ] -> [ Edge | ]
}

null is only an outside-board pattern atom. It is not an object, cannot be combined with other cell tokens, and is not written as no null.

PuzzleStudio Documents

Input Rules

Use input for a rule oriented by the current directional input.

rules {
input [ Player ] -> [ > Player ]
}

Bare input is the recommended form for the built-in up, down, left, and right inputs. It uses the current direction as the rule orientation.

The explicit set form, such as input horizontal or input directions, is for a rule that intentionally restricts or exposes its accepted direction set. Prefer bare input for ordinary four-direction movement.

> marks the direction on the matched object.

PuzzleStudio Documents

Movement

Use move after rules have marked objects with direction.

rules {
input [ Player ] -> [ > Player ]
[ > Player | Box ] -> [ > Player | > Box ]
move
}

The first rule marks the player. The second rule passes that direction to a box.

move applies the marked movement and blocks movement into occupied cells in the same layer.

PuzzleStudio Documents

Win Conditions

Use win_conditions for checks that clear the current level.

Object Goals

win_conditions {
some Goal
all Goal on Box
}

This level clears when there is at least one Goal and every Goal has a Box on it.

Expression Checks

win_conditions {
some(Goal)
no([ Goal no Box ])
}

Expression checks are useful when the clear condition is easier to read as board queries.

Multiple Lines

win_conditions {
all Goal on Box
no Enemy
}

Every line in win_conditions must be true before the level clears.

Visuals

Use visuals to define how objects look.

The 2D Visual pane's **PNG** button downloads the selected frame, and **GIF** downloads all animation frames in order as a looping animation. A static visual exports as a single frame. Files use the visual name and native pixel dimensions; grids, selection outlines and checkerboards are excluded. Exporting preserves the draft, source, frame selection and playback.

PNG preserves transparency, including partial alpha. GIF supports binary transparency: alpha below 128 becomes transparent, and alpha of 128 or above becomes opaque while retaining its RGB color. Frame delays follow the preview's total duration divided by frame count, rounded to 10 ms with a minimum of 20 ms per frame for browser playback. Fast animations can therefore export slower. These image exports apply to 2D visuals.

The 3D Visual pane's **VOX** button downloads a MagicaVoxel .vox file with all animation frames in draft order. A static visual contains one model. It saves the complete voxel volume at its original size, including colors and empty space, regardless of the selected editing slice or camera angle. Export leaves the draft and source unchanged.

VOX readers with shape-animation support can use the saved frame sequence; readers without it may show only one frame. Set the playback speed in the receiving tool. RGBA palette values are retained, but transparency rendering depends on the reader's material support. Game transforms, lighting and camera settings are not included.

puzzle sokoban {
visuals {
Player {
image "visuals/player.png"
}

Box {
#b5651d #f4a261
00000
01110
01110
01110
00000
}
}
}

Image visuals use a workspace-relative path. ASCII visuals use a palette row followed by rows of palette indexes.

Visuals are drawn into one cell by default. Use contain, cover, or stretch to choose the draw box and scaling:

visuals {
Gate {
image "visuals/gate.png"
contain 2 2
translate (0, -0.25)
}

Portrait {
image "visuals/portrait.jpg"
cover 1 1
}

Panel {
image "visuals/panel.png"
stretch 2 1
}
}

Use layers for state exclusion and drawing order, and legend for level characters.

Visual spatial operations use translate [world|local] <vector>. A 2D visual uses rotate [world|local] <angle> [from <angle>], for example rotate directions from up. A 3D visual may use the same from and axis-less forms; an omitted axis defaults to +Z (up). Use around <axis> for another axis, for example rotate local facing from 0deg around right. The removed offset, rotate using, and generic transform forms are not accepted. For four-way 3D variants authored facing front, use Arrow:horizontal { rotate horizontal from front }.

Both model kinds use visuals. In a reusable ASCII shape, > starts the next animation frame and - starts the next -Z (down) layer; 2D visuals must have depth 1. ASCII columns increase toward right (+X), while rows increase in source order toward back (-Y).

Several visuals { ... } blocks in one puzzle share one owner scope. Shapes and palette names declared in any fragment can be used by visuals in another.

Drawing order belongs to layers:

layers {
priority = down right
floor = Floor
merge {
actor = Player
goal = Goal
effect = !Spark
}
box = Box !Box
}

Rows run back to front. A normal name participates in both state storage and rendering; !Visual participates only as a transient animation visual. Rows inside merge remain separate state layers but share one unordered render priority. Overlapping pixels or voxels average their non-transparent RGBA channels. Direction priority compares owner-cell coordinates lexicographically. Use two distinct axes in 2D and three in 3D (priority = down right front, for example).

Guards

Use if when a block should run only when a check is true.

rules {
if count(Box) == 0 {
next_level
}
}

The guarded block runs only when the condition is true.

Named conditions can also be used inside if.

PuzzleStudio Documents

Fix

Use fix when a group of rules should repeat or be limited together.

rules {
fix once {
[ Player | Coin ] -> [ Player | ]
[ Player | Key ] -> [ Player | ]
}
}

fix once gives each contained rewrite the once application mode. It fixes the enclosed rules' defaults; it does not make the whole block a new routine or repeat the block as a unit.

PuzzleStudio Documents

Routines

Use a routine to name and reuse a list of rule statements. A declaration has a name and body. Calling its name executes that list once.

routine push {
[ > Player | Box ] -> [ > Player | > Box ]
}

rules {
input [ Player ] -> [ > Player ]
push
animate move
}

Execution Prefixes

Application and animation prefixes apply to rewrites, calls, and blocks. Write application first, animation second, and a rewrite's orientation last.

once instant input [ Player ] -> [ > Player ]
repeat animate settle
once instant {
update_shadows
update_markers
}

repeat settle means repeat { settle }: repeat the whole sequence until it stops changing. A prefix does not replace explicit control flow inside a routine. To make repetition part of the routine itself, write the block in its body.

routine spread {
repeat {
once [ Fire | Wood ] -> [ Fire | Fire ]
once [ Fire | Grass ] -> [ Fire | Fire ]
}
}

once spread calls the routine once, including its internal repeated block. random { ... } chooses one applicable statement deterministically.

Scoped Defaults

fix sets defaults for statements in its body, including called routines. Explicit inner prefixes take precedence; leaving the scope restores its caller's defaults. Application defaults affect rewrites, not how often a call runs.

fix once instant {
update_shadows
animate move
}

Direction prefixes belong to rewrite patterns. Use fix right { ... } to give contained rewrites a default direction.

PuzzleStudio Documents

Rule Application

Application keywords decide how many matches a rewrite applies.

Repeat

A rewrite without an application keyword uses repeat: it keeps applying the same concrete rewrite until no match remains.

[ Fire | Wood ] -> [ Fire | Fire ]

Once

once applies only the first match in board order.

once [ Coin ] -> [ ]

once_all collects all matches from the state at the start of the rule and applies each collected match at most once. New matches created by those writes are not included.

once_all [ Ice ] -> [ Water ]

once_per_level lets a concrete rule fire once until restart or level change.

once_per_level [ Player Goal ] -> message "Goal reached"

Random

random applies one available match. The choice is deterministic for the same game state and input, so it remains visible to replay and solver behavior.

random [ Spark | Wire ] -> [ | Spark ]

Use fix once { ... } when several enclosed rewrites should share the same default. An explicit keyword on a contained rewrite overrides the fix value.

PuzzleStudio Documents

Patterns

Patterns describe cells and spatial relationships on the left and right side of a rewrite.

Rows And Orientation

Separate cells in a row with |. Prefix a pattern with left, right, up, or down when its orientation is fixed.

right [ Player | Box | no Wall ] -> [ | Player | Box ]

Bare input uses the current directional input as the orientation.

input [ Player | Box ] -> [ > Player | > Box ]

Rectangles

Separate rows inside one bracket block with ; to match a rectangle. Every row must have the same width.

down [ Player | Box ; no Wall | Goal ]
  -> [ | Player ; no Wall | Goal Box ]

Variable Gaps

Use ... between pattern cells when any non-negative distance may separate the two sides.

once right [ Laser | ... | Target ] -> [ Laser | ... | Ash ]

Absence And Outside

no Wall requires a cell without Wall. An empty pattern cell matches a board cell without a positive object requirement. null matches outside the stage; it is not an object and cannot be written as no null.

once right [ Edge | null ] -> [ Edge | ]

PuzzleStudio Documents

Rule Effects

Effects request work outside a board-cell replacement. Write an effect by itself or after a matching rewrite.

Finish Or Control A Turn

rules {
once [ Player Trap ] -> cancel
once [ Player Goal ] -> win
once [ Conveyor Player ] -> [ Conveyor > Player ] again
}

cancel restores the state from the start of the current turn, including board, mark, and variable writes. win clears the level through the normal on_level_clear lifecycle. again commits the current turn and requests a follow-up turn without repeating the previous input.

Emit Feedback

rules {
once [ Player Coin ] -> [ Player ] sfx pickup
once [ Player Goal ] -> message "Goal reached"
}

sfx emits a named sound declared in sounds. message accepts quoted text or a text value. These are observable turn results; they are not board objects.

Level And Scene Effects

rules {
restart -> restart
if win_conditions -> next_level
if input == skip -> goto "bonus"
}

Puzzle rules can emit restart, next_level, scene navigation, or a quoted local-level jump such as goto "bonus". A quoted level id must exist in the same puzzle. Normal level clear should use win_conditions or win; use explicit navigation for an intentional flow change.

Several effects may be clearer as separate lines inside if, lifecycle, or routine blocks. Do not use an effect wrapper or then separator.

Messages

Use message to show text before or after a level map.

levels {
level intro {
message "Push the box."
PBG
message "Room clear."
}
}

Messages before the map run when the level starts.

Messages after the map run when the level clears.

Lifecycle shorthand requires a braced level. An unbraced level contains only map rows.

PuzzleStudio Documents

Variables

Use variables for values that can change while the puzzle runs.

Basic Variables

var button_is_pushed = false
var moves = 0

var creates a named value. Rules and lifecycle blocks can update it.

rules {
once [ Player Coin ] -> [ Player ] moves += 1
if moves >= 20 {
button_is_pushed = true
}
}

Write updates as <name> <operator> <value>. Assignment uses =, and integer variables also accept +=, -=, *=, /=, and %=. The removed set prefix is not accepted.

Constants

const target_moves = 12
const door_color = "blue"
const title = "Level Select"

const creates a named value that stays the same. Names such as title, author, or homepage have no special declaration or compile behavior; a scene may display any constant through a text component.

Persistent Variables

save cleared = false

save behaves like ordinary mutable state and keeps its value across restart and level load. It is included in the host save record and in undo/redo within the active level.

PuzzleStudio Documents

Marks

Use marks for short-lived facts that help a rule chain run.

Declare Marks

marks {
visited
armed = bool
intent = directions
count = int
}

A bare mark name is a flag. A typed mark stores either a boolean, an integer, or one value from a named value set.

Mark Objects

rules {
[ Box ] -> [ Box{armed} ]
[ Box{armed} ] -> [ Box{no armed} ]
}

Marks can be added to objects and removed again inside rules.

Movement Intent

rules {
input [ Player ] -> [ > Player ]
move
}

Directional movement uses a temporary direction mark. move applies that direction after the input rule runs. All marks are transition-local and are cleared after the transition; use var for saved puzzle state.

PuzzleStudio Documents

Conditions

Use conditions for named checks derived from the current board.

Count Objects

condition cargo_count = count(Box)

count(Object) returns how many matching objects are on the board.

Check Presence

condition any_goal = some(Goal)
condition no_open_goals = no([ Goal no Box ])
condition some_box_on_goal = some([ Goal Box ])

some and no describe whether matching objects or patterns are present.

Use A Condition

rules {
if no_open_goals {
next_level
}
}

Use a condition name inside if when the same check should stay readable or be reused.

PuzzleStudio Documents

Lifecycle

Use on_* blocks for named moments in a puzzle or scene.

scene title {
on_scene_start {
stop_music theme
}
}

on_scene_start belongs to a scene. on_level_start and on_level_clear belong to a puzzle model; do not move model setup through a fake player input.

A puzzle automatically creates a same-named playable scene unless an explicit scene replaces it. In that standard case, on_scene_start may be written directly inside the puzzle beside layout and keys.

puzzle sokoban {
on_scene_start {
play_music theme
}
}

When on_level_clear is omitted, the default program performs await, then wait, then next_level. An explicit on_level_clear replaces that whole program, so include next_level when the game should still advance.

Put setup, music, messages, and level advancement in the hook that names when they should happen.

PuzzleStudio Documents

Groups

Use groups to create selector aliases in one block.

groups {
pushable = Box Crate
}

Groups keep rules readable when several objects behave the same way.

rules {
[ > Player | pushable ] -> [ > Player | > pushable ]
}

Use a group name where you would otherwise list the same objects repeatedly.

PuzzleStudio Documents

Tags

Use tags to define ordered sets of object-name atoms for schema axes.

tags {
color = red blue
}

puzzle color_boxes {
layers {
Player Box:color Wall
}
}

Box:color expands into object identities such as Box:red and Box:blue.

When a tag set contains object-name atoms, a qualified selector appends the suffix to each atom. For example, pair:a with pair = A B resolves as A:a B:a.

Built-in tag sets include directions, horizontal, and vertical.

PuzzleStudio Documents

Maps And Expansion

Tags define finite value sets. for expands authoring syntax over a set or numeric range, while map translates one bound value into another.

Expand A Rule

for d in directions {
once d [ Player | Box ] -> [ Player | Box ]
}

Prefer bare input for normal four-direction movement. Use for when the expanded value is needed in several positions or expressions. for is an authoring-time projection, not a menu or runtime loop.

Numeric ranges are inclusive.

for n in 1...3 {
once [ Gate:n ] -> [ Gate:n ]
}

Range endpoints may be integer literals or integer var / const values whose initial value is known while authoring is expanded. Updating the variable during a turn does not change the generated rules.

Translate Values With Map

map opposite directions {
up -> down
right -> left
down -> up
left -> right
}

A map call consumes a value already bound by a selector or for expansion.

for d in directions {
once d [ Arrow:d ] -> [ Arrow:opposite(d) ]
}

Maps can also drive visual table lookup. They do not create objects, tags, or runtime variables. The map input and every output must belong to the declared tag set.

Layout for follows the same projection principle, but it only creates layout children. It does not gain cursor movement, selection, or level-menu behavior. level_menu uses this projection during authoring, then lowers the generated items to ordinary button components inside a normal container. The renderer scrolls any scene container whose measured content exceeds its viewport.

PuzzleStudio Documents

Scenes

Use scene blocks for screen flow outside the board.

scene title {
layout {
title
button "Start" -> goto playing
}
}

Scenes can show text, menus, puzzle slots, and other layout components.

Use goto to move to another scene while preserving its state. Use start when the target scene should be initialized before entry. A top-level model gets an automatic same-named playable scene unless an explicit scene overrides it.

PuzzleStudio Documents

Scene Layout

Use layout only when the default puzzle screen is not enough.

Most single-board games do not need a layout block. A lone puzzle sokoban gets a playable screen automatically.

puzzle sokoban {
layout {
heading title
sokoban
}
}

The model name, here sokoban, displays that puzzle board.

Use an explicit scene when you need a title screen, menu, or level select screen.

scene title {
layout {
heading title
button "Start" -> goto sokoban
}
}

heading, subheading, text, and caption are text roles. button, toggle, and audio_controls are interactive controls. row, column, and box are containers. Layout allocation uses space_fit or space_fill <weight>; aspect <w> <h> controls ratio. Layout does not use CSS sizes or the removed size <w> <h> form.

toggle binds to a schema-backed boolean render setting. Use an explicit puzzle target when the scene can see more than one instance.

layout {
toggle "Shadows" = board.render.shadow
toggle "Orthographic" = board.render.camera.orthographic
audio_controls
}

audio_controls edits session audio enablement and volume. Those values do not participate in puzzle undo, restart, or level navigation. The control has a fixed intrinsic width and uses space_fit; place it with its parent container rather than giving it space_fill or an aspect ratio.

PuzzleStudio Documents

Semantic Inputs

Use owner-scoped keys to map physical keys to semantic inputs, scene routines, or explicit scene effects.

puzzle sokoban {
keys {
w ArrowUp -> input up
s ArrowDown -> input down
a ArrowLeft -> input left
d ArrowRight -> input right
r -> input restart
}
}

The left side lists raw keys. In a puzzle the right side is a semantic input. In a scene it may instead name a scene-local routine or a direct effect such as goto title. The old inputs { input <- keys } form is not canonical syntax.

Direction inputs up, down, left, and right have standard built-in key mappings; add keys only to override or extend them.

PuzzleStudio Documents

Menus

Use buttons and commands to build menus.

scene menu {
layout {
text "Menu"
column {
button "Resume" -> input resume
button "Restart" -> playing.restart
button "Level Select" -> goto level_select
}
}

keys {
Escape Enter Space -> resume
}

routine resume {
goto playing
}
}

Use target-qualified commands such as playing.restart or board.restart when a command should operate on a specific target.

Use button for every item activated by the standard selection cursor, click/tap, or an explicit key binding. level_menu { ... } is authoring sugar for a normal column containing a level projection made of ordinary buttons and typed level transitions. Scene containers scroll only when their typed layout enables it. The generated level column uses space_fill 1 scroll true, so fixed siblings remain outside its viewport.

Name the level pack when more than one is visible. Progress options are normal authoring settings on the projection:

level_menu campaign {
show_index = true
show_solved = true
locked = true
unlocked_ahead = 1
columns = 4
}

With locking enabled, the first unlocked_ahead levels and that many levels beyond the furthest cleared level are available. Hidden levels do not enter the component tree, focus order, or pointer hit testing. This policy affects only that menu; it does not authorize or block explicit scene navigation elsewhere.

PuzzleStudio Documents

Scene State And Effects

A scene owns screen-local state, layout, input dispatch, and navigation. It does not reinterpret puzzle source or board state.

Instance Declarations

scene playing {
var message = "Push the box"
layout {
text message
puzzle board = sokoban
}
}

Within layout, puzzle board = sokoban creates the scene-local model instance and places its model window. That window owns the normal semantic-input route to the slot's rules program. Explicit cross-world calls use member syntax, for example hub.board.mark or hub.board.rules.

Scene var and const values belong to the scene instance. Puzzle variables belong to their model; top-level values belong to the session. Keep state in the smallest owner that explains it. state { ... } is not scene syntax.

Parameterized scene instances use the same typed call shape in root and layout positions:

scene message(content: string) {
aspect 4 1
layout {
text content
}
}

scene playing {
var notice = "Push the box"
layout {
message(notice)
}
}

Parameters are immutable within the created instance. Changing notice reconstructs the child in the same layout slot. When that child is already mounted, show message and hide message change only that slot's visibility. Showing an unmounted scene creates an overlay; bare hide closes the focused overlay and resumes its caller.

Navigate Or Reinitialize

scene title {
layout {
button "Continue" -> goto playing
button "New Game" -> start playing
}
}

goto enters a scene while preserving its existing state. start initializes the target scene first. A level scene can receive a quoted level id, such as goto sokoban("warehouse").

Explicit State Effects

Scene routines and controls may use target-qualified effects.

scene pause {
layout {
button "Restart" -> playing.restart
button "Next Level" -> playing.next_level
}
keys {
Escape -> goto playing
}
}

Use clear_undo_history to discard only undo history. clear_game_progress also resets cleared levels, current-level selection, and persistent variables. More focused operations include reset persistent_vars, reset <variable>, set current_level = <level>, and clear current_level.

These effects are explicit interventions for menus, hubs, and debug controls. Ordinary clear, advance, and restart behavior remains owned by the puzzle model and its lifecycle.

PuzzleStudio Documents

Display

Object rendering is configured through visuals. State and rules use the same object names that are declared in layers.

PuzzleStudio Documents

Theme

Use theme to set presentation colors and an optional project font. The three public colors are anchors: themes derive surfaces, borders, muted text, controls, focus, and board colors by mixing them instead of exposing more component-specific color settings.

theme studio {
accent_color = #2f7d62
background_color = #f7f5ef
text_color = #1d2522
font = "fonts/interface.ttf"
}

font accepts a game-relative .ttf or .otf path. Standalone exports include the referenced font bytes and the browser renderer uses that same font asset.

Themes resolve typography, UI surfaces, board framing, interaction cues, render treatment, and motion for exported play surfaces. When font is omitted, the theme's standard font is used; studio includes a sans-serif font.

Authored colors are kept exactly as specified. Color contrast is not a compiler diagnostic.

The standard themes are studio, pencil, and the PuzzleScript compatibility profile puzzlescript. pencil keeps the studio presentation and changes only the built-in font to the handwritten family.

Use visuals for object drawings and themes for surrounding presentation.

PuzzleStudio Documents

Rendering

Model-owned rendering options belong in render. They affect presentation, not board state, collision, win conditions, or solver state.

Grid And Animation

puzzle sokoban {
render {
grid {
type = occupied_cells
}
animation {
    default = animate
    duration = 160ms
}
}
}

type = occupied_cells outlines cells containing objects. type = all_cells includes empty cells, while type = hidden turns the grid off. Omitting the setting is equivalent to hidden.

animation.default selects animate or instant for statements without a local display prefix. duration and easing are independent settings, so an instant default can still configure how an explicit animate behaves. Omitted values are instant, 250ms, and linear. Easing accepts linear, ease_out, step, and spring.

Use animate / instant on a rewrite, routine call, or block. Use fix animate { ... } / fix instant { ... } for scoped defaults. Inner explicit settings take precedence, including inside called routines. These settings control rule-generated movement, appearance, disappearance, replacement, and direction rotation; explicit waits, sound, and visual clip playback keep their own behavior.

Rules update the same typed settings by full path:

rules {
if input == reveal_grid {
render.grid.type = all_cells
}
if input == turn_camera {
render.camera.yaw += 10
}
}

Do not prefix setting updates with set. Setting changes belong to the play session and participate in undo, redo, checkpoint, and restart, but remain outside puzzle state and solver search.

Use await to synchronize rules with presentation. It commits the current rule segment and pauses the turn until every animation emitted since the previous await has finished. If there is no pending animation, execution continues immediately.

rules {
input [ Player ] -> [ > Player ]
move
await
once [ Player Goal ] -> message "Arrived"
}

wait is a timeline delay instead. Bare wait uses default_wait_time; a form such as wait 300ms uses that duration. await, wait, and message are separate continuation boundaries, so consecutive pauses complete one at a time. The remaining rules resume in the same turn, and one undo still returns to the state before the input.

When presentation is busy, input_buffer selects the model input policy. busy_input = reject rejects new input. busy_input = queue retains one input and requires queued_presentation = preserve, skip, or accelerate. accelerate may also set min_wait.

input_buffer {
busy_input = queue
queued_presentation = accelerate
min_wait = 50ms
}

PuzzleStudio Documents

Visual Shapes And Animation

Use shapes for reusable visual patterns and visuals to bind those patterns, colors, images, and transforms to object selectors.

Reusable Shapes

shapes {
arrow {
..0..
.000.
..0..
..0..
.....
}
}

visuals {
Player {
#2d6cdf
shape = arrow
}
}

shapes owns visual data only. Object identity and collision still come from layers. Use shape = <name> when a bare row could also be valid ASCII and would therefore be ambiguous.

Frames And Voxel Layers

Inside a shape, a line containing only > starts the next animation frame. In a 3D shape, a line containing only - starts the next -Z (down) voxel layer of the same frame. Do not put blank lines around these separators.

visuals {
Beacon {
duration 400ms
#ffd166 #ef476f
000
010
000
>
111
101
111
}
}

2D visuals must remain one voxel layer deep. Both 2D and 3D use the same visuals, palette, shape, and frame vocabulary.

Spatial Operations

visuals {
Arrow:directions {
#ffffff
shape = arrow
rotate directions from up
translate local (0, -0.25)
}
}

Rotation is rotate [world|local] <angle> [from <angle>]. In 3D, the same axis-less form rotates around +Z (up); append around <axis> to select another axis. Operations run in source order; put a transform on the visual reference that needs it rather than deriving rotated shapes globally. For a four-way 3D visual authored facing front, Arrow:horizontal { rotate horizontal from front } expands the variants around Z with front as the zero rotation.

Text Overlays

A 2D visual may place one text overlay above its solid, ASCII, or image base. The overlay shares the visual's transform, animation, and opacity.

visuals {
Label {
#20242b
0
text "A" {
font_size = 0.5
align = bottom_right
overflow = visible
color = #ffffff
}
}
}

font_size is relative to cell height. align uses the nine compass-style positions from top_left through bottom_right; the default is center. overflow is clip by default or visible. Text overlays are currently 2D only and cannot be placed in an unordered merge composition.

PuzzleStudio Documents

3D

Set dimension = 3 inside a puzzle to make it a three-dimensional grid model. It uses the same layers, rules, levels, and visuals concepts as a 2D puzzle; there are no separate puzzle3 or levels3 forms.

Level Depth

A line containing only - starts the next Z layer in a 3D level. The . character follows the shared levels contract: it is always empty and cannot be remapped in either dimension.

Camera And Viewport

puzzle push3d {
dimension = 3

layers {
actor = Player
}

render {
camera {
orthographic = false
yaw = 34
pitch = 38
roll = 0
zoom = 1
interactive_look = true
interactive_zoom = true
}
grid {
type = occupied_cells
}
viewport {
smoothscreen 7 7
focus Player
}
pixelate {
enabled = true
scale = 4
smoothing = true
}
shade = true
shadow = true
}

visuals {
Player {
#4f7cff
0
}
}

rules {
once input horizontal [ Player | no Player ] -> [ | Player ]
}

levels {
legend {
P = Player
}

level "start" {
P
-
.
}
}
}

camera defines the initial view. orthographic = true selects orthographic projection; the default is perspective. roll rotates the image plane around the view direction and defaults to 0. Camera block settings use normal typed assignments, including interactive_look = true and interactive_zoom = true. The equivalent inline shorthand is camera yaw=34 pitch=38 interactive_look interactive_zoom.

Pointer look and zoom are component gestures, not semantic puzzle inputs. viewport frames a world-space region around its focus; it does not hide objects outside that region. zoomscreen snaps to the target and smoothscreen follows it gradually.

pixelate lowers the browser surface render resolution and scales it with nearest-neighbor sampling. smoothing controls antialiasing at that reduced resolution. shade selects lit or unlit voxel materials, while shadow enables cast and received shadows. Shadows are disabled by default. A 3D object without a visual is not given an implicit cube.

Rules update the same typed settings by their full paths, for example render.camera.yaw += 10 or render.grid.type = all_cells. Setting changes belong to the play session and participate in undo, redo, checkpoint, and restart. They remain outside puzzle state and solver search; state that changes gameplay must be represented by objects or puzzle variables.

Voxel Visuals

PuzzleStudio's canonical game coordinates increase right (+X), front (+Y), and up (+Z). ASCII columns increase X, while rows and layers move toward -Y (back) and -Z (down). Slice 1 is the first ASCII layer, and increasing the slice number moves down while decreasing Z.

3D visuals use - for the next -Z voxel layer and > for the next animation frame. A color-only visual is a filled 1x1x1 voxel. Use shape = <name> to reference a reusable voxel pattern from shapes.

Sounds

Use sounds to name sound effects and music.

sounds {
sfx step { seed = step; type = step; volume = 0.45 }
sfx splash { seed = splash; type = water; volume = 0.7 }
sfx box_drag { seed = box-drag; type = drag; volume = 0.75 }
sfx clear { seed = clear; type = jump; volume = 1 }
music theme {
seed = main
height = 0.5
bars = 8
bpm = 105
volume = 0.5
slots {
count = 9
seed = theme-sound
slot 2 {
seed = fixed-two
}
}
}
sfx impact audio/impact.wav
music title_theme audio/title.mp3
}

puzzle sokoban {
sounds {
move Player -> sfx step
move Box -> sfx box_drag
}

on_level_clear {
sfx clear
next_level
}
}

Generated sounds use a block with seed and generation settings. External audio uses sfx <name> <path> or music <name> <path>. Paths are relative to the game folder and may use .mp3, .mp4, .ogg, or .wav. The direct reference is the asset declaration; no separate file manifest is needed.

Generated music keeps composition and sound independent. seed determines the events and is also the default parent for anonymous, exchangeable slots. slots.count selects 1 through 32 slots and defaults to 9. slots.seed replaces the parent for the whole set. slot 1 through slot count override individual seeds; unspecified slots continue to inherit. Every slot samples the same probability model, and a slot override changes timbre without changing events.

Put movement sounds in the puzzle. Put scene music in scene lifecycle. Put clear sounds in level lifecycle. sfx plays once, while music loops until a scene effect replaces or stops it.
