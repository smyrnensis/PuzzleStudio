# パズルゲームフレームワーク 設計思想

> PuzzleScriptにインスパイアされたターンベース・グリッドベース・ルール駆動型パズルゲームフレームワークの設計思想をまとめたドキュメント。
> フレームワーク/エンジン非依存の内容として記述する。

---

## 1. ゲームの本質

### ジャンルと目標
- **ターンベース・グリッドベースのパズルゲーム**を作るためのフレームワーク
- PuzzleScript の設計思想を継承し、Baba Is You のような「ルール駆動」のパズルを構築可能にする
- 最終目標は「**データを入れるだけでゲームが完成するフレームワーク**」

### コアゲームプレイループ
1. プレイヤーがキーボードを操作する（連続的なイベント）
2. 入力が離散的な InputEvent に変換される（連続→離散の境界）
3. InputEvent に応じて、定義されたルールが順次適用される（離散→離散）
4. ルールによって盤面（GameState）が更新される（離散→離散）
5. 新しい盤面が画面に描画される（離散→表示）
6. クリア条件を判定する

## 2. 設計原則

### 2.1 純粋関数としてのゲーム
ゲームを数学的な関数として捉える：

```
Game = (InputEvent, GameState) -> GameState
```

- **完全性**: すべてのロジックは入力と状態のみに依存する
- **決定性**: 同じ入力と状態は常に同じ結果を生成する
- **テスタビリティ**: ゲームロジックはエンジンから完全に独立して単体テスト可能
- **再現性**: 入力履歴を記録すればリプレイ・デバッグが完全に可能

### 2.2 データとしてのルール
ゲームロジックをハードコードせず、**宣言的なデータ（JSON）として記述する**。ルールは「パターンAをパターンBに変換する」というパターン置換で表現される。これにより：
- ルールの追加・変更にコード変更が不要
- ゲームデザインの反復が高速
- 人間が読みやすい形式を保てる

### 2.3 エンジンとロジックの完全分離
- フレームワーク（汎用ルールエンジン）と個別ゲームのデータ（ルール、レベル、スプライト）を明確に分離する
- ルールエンジンはどのゲームエンジン上でも再実装可能な設計にする

### 2.4 制約による明確性
意図的に強い制約を課すことで、複雑さを制御する：
- **グリッドベースのみ**: すべてのゲーム要素は格子上に配置。自由座標は使わない
- **ターンベースのみ**: リアルタイム要素を完全に排除
- **離散データのみ**: システム内部に連続値は存在しない。Bool型、Int型、列挙型（文字列）のみでゲーム状態を表現する。float型は使用しない

### 2.6 入力の離散化
キーボード入力は本質的に時間軸（連続）を持つが、ゲームシステムに入る時点で離散イベントに変換する。

```
Keyboard (continuous) → [discretize] → InputEvent (discrete) → Engine
```

- 入力の離散化はシステムの最外縁で1回だけ行う
- 離散化以降、システム内部に連続データは一切流れない
- Engine が受け取る InputEvent は時間情報を持たない純粋な離散値（方向の列挙、操作の種類）
- これにより Engine の純粋関数性（2.1）が保証される

### 2.5 イミュータブルな状態操作
GameState は直接変更せず、常に新しいインスタンスを生成する。これにより：
- undo/redo の実装が自然に可能
- 状態の整合性が保証される
- デバッグ時に任意の過去状態を参照できる

## 3. ルールシステムの設計

### 3.1 ルールの原理：パターンマッチングと置換

```
Rule: Pattern_Before -> Pattern_After
```

1. 現在の盤面から `before` パターンに一致する箇所を左上から順にスキャンして検索
2. 一致した箇所のグローバル条件（`conditions`）をチェック
3. 条件を満たせば、`after` パターンで置換
4. 副作用（`effects`）を適用

### 3.2 オブジェクト単位の精密な置換
セル全体を上書きするのではなく、**マッチしたオブジェクトのみを置換**する：
- ルール `[A] -> [C]`, セル `["A", "B"]` → 結果 `["C", "B"]`（B は影響を受けない）
- ルール `[A] -> []`, セル `["A", "B"]` → 結果 `["B"]`（A だけ消え、B は残る）

### 3.3 適用方式
- **"once"**: 盤面上で最初に一致した1箇所のみに適用して次のルールに進む
- **"until_stable"**: 盤面に変化がなくなるまで同じルールを繰り返し適用する（重力やカスケード処理に使用）

### 3.4 方向システム
パターンの方向指定：
- `none`: 方向の区別なし（1x1パターン等）
- `up` / `down` / `left` / `right`: 特定の1方向のみ
- `vertical`: 上下の2方向
- `horizontal`: 左右の2方向
- `any`: 4方向すべて（1つのルール定義から最大4つのバリアントを自動生成）

相対方向タグ（`>`, `<`, `^`, `v`）と絶対方向タグ（`right`, `left`等）の区別があり、相対方向はルールの回転に追従して変換される。

### 3.5 パターン内のセル条件
`before` ブロック内のセルには3種類の条件を指定できる：
- **`objects`**: 置換対象。そのセルに指定オブジェクトが存在し、`after` ブロックで置き換えられる
- **`has_objects`**: チェックのみ。存在確認だが、置換対象にはならない
- **`no_objects`**: チェックのみ。不存在確認（壁がないことの確認等）

### 3.6 複数パターンブロック
1つのルール内に複数の独立した `before`/`after` ブロックを持つことができる：
- 各ブロックは独立した位置にマッチ可能（位置関係に制約なし）
- すべてのブロックがマッチした場合のみ、すべての `after` ブロックが同時に適用される
- 用途例：「プレイヤーがボタンを押すと、別の場所のゲートが開く」

### 3.7 タグバインディング
`$` で始まるタグは変数バインディングとして機能する：
```
[Player:$color] -> [Box:$color]
// Player:red なら Box:red に変換される
```
`before` でマッチしたタグの実際の値を記録し、`after` で同じ変数名を使うことで値を継承できる。

### 3.8 ルールグループ
- ルールはルールグループに整理される
- グループ自体にも `application`（`once`/`until_stable`）が設定可能
- グループ内のルールが安定するまで繰り返し実行できる
- グループは配列の順序で逐次実行
- `call` エフェクトによる他グループの呼び出しが可能

### 3.9 条件とエフェクト
- **条件（conditions）**: グローバル変数に対する論理式。ルールの適用前に評価される
  - 例: `score >= 10 && some_flag == true`
- **エフェクト（effects）**:
  - `set`: グローバル変数を特定の値に設定
  - `change`: グローバル変数を加減算
  - `sound`: サウンド再生
  - `message`: メッセージ表示
  - `call`: 別のルールグループを呼び出す

### 3.10 処理の原子性
1つのルール適用は「完全に成功するか完全に失敗するか」の原子性が保証される。複数セルの同時変更でも中間状態が他のルールから観測されることはない。

### 3.11 決定論的実行の保証
パターンマッチングは厳密な順序（左上から右下へのスキャン、方向の優先順位）で実行され、同一条件下では常に同一結果を生成する。パズルゲームにおいて結果の予測可能性はゲームデザイン上不可欠。

## 4. データ構造

### 4.1 GameState（ゲーム状態）
ゲーム全体の状態は以下の2つの要素で構成される。内部表現は実装言語・フレームワークに適した形式を選択してよい。

- **global_state（グローバル状態）**: 盤面に紐付かない状態変数のキーバリューストア
  - サポートする型: int, bool, String
  - 用途: スコア、移動回数、フラグ等
- **puzzle_state（盤面状態）**: 2次元グリッド。各セルはオブジェクトのリストを保持する
  - `puzzle_state[y][x]` でセルにアクセス
  - 1つのセルに複数のオブジェクトが同居可能（例: Floor の上に Player がいる）

概念的な構造：
```
GameState
├── global_state: Map<String, int | bool | String>
└── puzzle_state: Puzzle[y][x] -> List<ObjectInstance>
```

### 4.2 オブジェクトの表現
オブジェクトは文字列で表現される：`"Name:tag1:tag2"` 形式
- `"Player"` — タグなし
- `"Player:right"` — 方向タグ付き
- `"Box:on_goal"` — 状態タグ付き

### 4.3 オブジェクト定義
各オブジェクトは以下の属性を持つ：
- **name**: 一意な名称（Player, Wall, Box, Goal 等）
- **layerId**: 描画レイヤー（重なり順序の制御）
- **properties**: 共通特性のリスト。ルール内で `@` プレフィックスで参照される
  - 例: `Movable`, `Solid`, `Falling`, `PlayerControlled`
- **tags**: 状態のバリエーション。コロン区切りで表現
  - 例: direction（up/down/left/right）、state（on_goal 等）

### 4.4 プロパティによる抽象化
個別のオブジェクト名ではなく、プロパティでルールを記述できる：
- `@Movable` — 移動可能なすべてのオブジェクト
- `@Solid` — 衝突判定を持つすべてのオブジェクト
- `@Falling` — 重力の影響を受けるすべてのオブジェクト

新しいオブジェクトを追加してもルールを変更する必要がない。

## 5. レベルデータ

### 5.1 ASCIIアート形式のマップ定義
```json
{
  "legend": {
    "P": ["Player"],
    "W": ["Wall"],
    "#": ["Box"],
    ".": ["Goal"],
    "X": ["Goal", "Box"],
    " ": []
  },
  "map": [
    "WWWWW",
    "WP.WW",
    "W.#.W",
    "W..XW",
    "WWWWW"
  ]
}
```

### 5.2 凡例（legend）システム
- 1文字のシンボルとオブジェクト配列のマッピング
- 1つのシンボルに複数のオブジェクトを割り当て可能（例: `"X": ["Goal", "Box"]`）

### 5.3 レイヤーの自動構築
レベルデザイナーはレイヤーを意識する必要がない。各オブジェクトがどのレイヤーに描画されるかは、オブジェクト自身の `layerId` 定義に従って自動的に正しいレイヤー構造が構築される。

### 5.4 レベル固有の設定
各レベルは独自のグローバル変数初期値を定義でき、レベルごとに異なるクリア条件や制約を設定できる。

## 6. アーキテクチャ（コンポーネント構成）

| コンポーネント | 責務 |
|:---|:---|
| **GameManager** | ゲーム進行の中央制御。GameState の唯一の所有者。入力処理、レベル管理、他システムとの調整 |
| **RuleProcessor** | ルール適用エンジン。GameState とルールデータを受け取り、新しい GameState を返すステートレスな処理系 |
| **ObjectDB** | オブジェクト定義のマスターデータ管理。プロパティ解決、インスタンス文字列の生成・解析 |
| **HistoryManager** | undo/redo 機能の提供。GameState のスナップショットをスタックで管理 |
| **LevelLoader** | レベルデータの読み込みと GameState の初期化 |

### 所有権と操作権限
- GameState の所有者は GameManager のみ
- RuleProcessor は読み取り + 変更後状態の返却のみ（直接変更しない）
- 外部コンポーネントは読み取り専用コピーのみ取得可能

---

## 7. undo/redo の設計方針

- GameState のスナップショットをスタックで管理する独立コンポーネント
- リスタート時は**履歴を保持する**（リスタートを undo できる）
- レベル終了時のみ履歴をクリア
- 最大履歴数は実質無制限

---

## 8. PuzzleScript文法からの変換パイプライン

- 開発者は PuzzleScript 文法でルールを記述
- パーサーがそれを JSON 形式のルールデータに変換
- ルールエンジンは JSON データのみを扱う
- 人間にとっての可読性（PuzzleScript 文法）と機械にとっての処理しやすさ（JSON）を両立

## 10. まとめ：中核思想

> **「シンプルなルールの組み合わせから複雑な振る舞いを生み出す」**

PuzzleScript の実証済みの設計パターンを基盤としながら、以下の独自拡張を加える：
- より柔軟な UI・インターフェース
- グローバル状態管理
- ルールグループによるモジュール化
- タグバインディングによる汎用化
- 複数パターンブロックによる離れた位置間の連動

フレームワークが担保するのは「正しく動くルールエンジン」であり、そこに流し込むデータが「どんなパズルを作るか」を決定する。
