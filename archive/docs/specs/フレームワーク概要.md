# ルールベース・グリッドパズルゲームフレームワーク概要

> 詳細な型定義・API・アルゴリズムは `docs/フレームワーク計画.md` を参照。
> 設計原則の詳細は `設計思想.md` を参照。

## 1. 概要

### 1.1 ドキュメントの目的

本仕様書は、TypeScript + HTML5 Canvas 上で動作する、ターンベース・グリッドベースパズルゲームを開発するための共通フレームワークの設計概要を定義する。

### 1.2 技術スタック

| 項目 | 選定 |
|:---|:---|
| 言語 | TypeScript 5.x (strict mode) |
| ランタイム | Node.js 20+ LTS |
| パッケージ管理 | pnpm 9+ (monorepo workspaces) |
| ライブラリビルド | tsup |
| アプリビルド | Vite 6+ |
| テスト | Vitest (エンジンカバレッジ目標: 90%) |
| レンダリング | HTML5 Canvas 2D |
| 配布 | vite-plugin-singlefile (単一HTMLファイル) |

### 1.3 設計哲学

#### 純粋関数としてのゲーム

```
Game = (InputEvent, GameState) -> GameState
```

すべてのロジックは入力と状態のみに依存し、決定論的・再現可能・エンジン非依存にテスト可能。

#### データとしてのルール

- ゲームロジックは宣言的なデータ（JSON）で記述される
- ルールは「パターンAをパターンBに変換する」パターン置換
- ルールの追加・変更にコード変更は不要

#### 制約による明確性

- **グリッドベースのみ**: すべてのゲーム要素は格子上に配置
- **ターンベース**: リアルタイム要素は排除
- **整数のみ**: float型は使用せず、number (整数)・boolean・string のみ
- **イミュータブル状態**: GameState は常に新しいインスタンスを生成
- **原子的ルール適用**: 各ルール適用は完全に成功するか完全に失敗する
- **決定論的実行**: 同一入力 + 同一状態 = 同一結果

#### 汎用性

汎用的なゲームフレームワークの部分と個別のゲームの情報を完全に分離。データ（ルール、レベル、スプライト設定）を入れるだけでゲームが完成するフレームワーク。

## 2. アーキテクチャ

### 2.1 パッケージ構造

```
PuzzleMaker/
├── packages/
│   ├── engine/        # コアルールエンジン（外部依存ゼロ、純粋TypeScript）
│   └── renderer/      # Web Canvas レンダラー（engine のみに依存）
├── apps/
│   └── playground/    # 開発・テスト用 Web アプリ（engine + renderer に依存）
└── games/             # 純粋 JSON ゲームデータ
    └── sokoban/       # 倉庫番サンプル
```

**依存ルール**: engine は DOM/Canvas を含む外部依存ゼロ。renderer は engine のみに依存。

### 2.2 データの分類

- **GameData**: オブジェクト定義、ルールデータ、ゲームメタデータ（静的・不変）
- **LevelData**: レベルごとの盤面定義、凡例、クリア条件（静的・不変）
- **GameState**: 現在の盤面状態 + グローバル変数（動的・イミュータブル）

### 2.3 コンポーネント構成

| コンポーネント | 責務 |
|:---|:---|
| **GameManager** | ゲーム進行の中央制御。GameState の唯一の所有者。入力処理、レベル管理、他システムとの調整 |
| **RuleProcessor** | ルール適用エンジン。GameState とルールデータを受け取り、新しい GameState を返すステートレスな処理系 |
| **ObjectDB** | オブジェクト定義のマスターデータ管理。プロパティ解決、パターン展開 |
| **HistoryManager** | undo/redo 機能の提供。GameState のスナップショットをスタックで管理 |
| **LevelLoader** | レベルデータの読み込みと GameState の初期化 |

**所有権ルール**: GameState の所有者は GameManager のみ。RuleProcessor は読み取り + 変更後状態の返却のみ。外部コンポーネントは読み取り専用コピーのみ取得可能。

### 2.4 実行フロー

```
1. Input:  プレイヤーからの入力を受信（キーボード → InputEvent への離散化）
2. Setup:  GameManager が _input_direction グローバル変数をセット
3. Rules:  turnSequence に従ってルールグループを順次適用
4. Update: 新しい GameState が確定
5. Check:  クリア条件を判定
6. Render: 新しい状態を Canvas に描画
```

**入力の設計**: プレイヤーの移動はルールとして定義される。GameManager は入力方向をグローバル変数 `_input_direction` にセットし、ルールがそれを参照してプレイヤーを移動させる。移動ロジックもデータ駆動。

## 3. ルールシステム

### 3.1 ルールの本質

ルールは **パターンマッチング** と **置換** の組み合わせ：

```
Rule: Pattern_Before → Pattern_After
```

- **Pattern_Before**: マッチング対象となる盤面パターン（2D配列）
- **Pattern_After**: 置換後の盤面パターン（2D配列）

### 3.2 ルール適用原理

1. **マッチング**: 現在の盤面から Pattern_Before にマッチする箇所を左上から順にスキャン
2. **検証**: グローバル変数に対する条件（conditions）をチェック
3. **置換**: マッチした箇所のオブジェクトのみを Pattern_After で置き換え（セル内の他オブジェクトは影響を受けない）
4. **エフェクト**: 副作用（変数変更、サウンド、メッセージ等）を適用

### 3.3 主要な機能

- **適用方式**: `"once"`（最初の1マッチのみ）/ `"until_stable"`（安定するまで繰り返し）
- **方向システム**: `none` / `up` / `down` / `left` / `right` / `vertical` / `horizontal` / `any`（自動回転バリアント生成）
- **セル条件**: `objects`（置換対象）/ `hasObjects`（存在確認のみ）/ `noObjects`（不存在確認）
- **タグバインディング**: `$variable` 構文で before のタグ値を after に継承
- **複数パターンブロック**: 1つのルールで複数の独立した位置をマッチ・同時置換
- **ルールグループ**: 名前付きグループ。`call` エフェクトで他グループを呼び出し可能
- **プロパティ指定**: `@Movable` で同じプロパティを持つ全オブジェクトを一括指定

## 4. パイプライン

```
PuzzleScript 文法（人間が読みやすい）
  → パーサー（スコープ外）
    → JSON ルールデータ（機械が処理しやすい）
      → ルールエンジン
```

**注**: PuzzleScript パーサーは初期実装のスコープ外。ルールは JSON で直接定義する。
